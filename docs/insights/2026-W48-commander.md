## 三、建议（ACT 列表）

### ACT-2026W48-1：AI Review 门禁建对照集，先测误报率与已知回归命中率再扩量
- **来源**：ai-loop 11-23 头条（Sashiko）+ daily 11-23 codex 校准（0.9.5 对照实验：20 回归命中 3→14、20 对照 12 个零告警、token +11%）
- **建议**：为 itu-code-manage 的 AI Review 建一个小型对照集：从历史工单中选 20 个确认有 bug 的变更 + 20 个确认干净的变更，跑现有 AI Review 统计「已知问题命中率」与「误报率（对照集告警率）」，同时记录单次审查 token 成本。数据出来后再决定是否扩大 AI Review 自动化范围，避免「看起来能抓 bug 就上量」。
- **作用于**：work-profile #3
- **预期收益**：Sashiko 用生产数据拿到了「捕获率 75.8% / 返修率下降 35%」的背书，我们目前的 AI Review 没有可引用的命中率/误报率数字——这是向团队争取扩大覆盖的谈判筹码，也是防止误报淹没信任的第一道闸。
- **成本**：中，约 2-3 人日（标注对照集 + 跑批 + 统计）。
- **风险**：低；对照集标注可能有争议，先小样本、双人复核标注。
- **下一步**：采纳后司令先出对照集选取标准（来源工单、时间窗、标注规则），交阿贰执行跑批。

### ACT-2026W48-2：给审批/恢复链路补两条负路径回归用例（拒绝→无生产写入；执行后未恢复→回到调查）
- **来源**：daily 11-25 codex（OpenAI 11-24 工程演示的两条失败路径）+ W47 ACT-4 三态用例的延续
- **建议**：在 W47 ACT-4 三态用例（正确执行/正确暂停/越权拒绝）基础上，增加两条断言：① 审批被拒绝后，检查 agent 未产生任何生产写入（工单/配置/外发）；② 修复已批准执行、但验收指标未恢复时，任务状态回到「调查中」而不是被标记为「已恢复」。这两条恰好是 OpenAI 演示里新增的失败路径，也是现有 eval 最容易漏掉的盲区。
- **作用于**：work-profile #1、#3
- **预期收益**：把「修复≠恢复」「拒绝≠结束」写成机器可验证的断言，直接支撑 W47 ACT-5 双指标（采纳率+生产恢复率）的落地——没有这两条负路径，恢复率指标会被「假结案」污染。
- **成本**：低-中，每条约 0.5-1 人日，可挂靠 W47 ACT-4 试点一起做。
- **风险**：低；依赖 ACT-5 选定的告警链路先确定，建议两者同步推进。
- **下一步**：采纳后与 W47 ACT-4/ACT-5 合并为一个「验收用例包」，由阿贰在 opencode-mt 评测链路一次落地。

### ACT-2026W48-3：Agent 工具链负路径验收——超时退出、失败上报、槽位释放
- **来源**：trending 11-25 codex 校准（stitch-skills PR #111：缺必需文件检查器仍返回 0；CLI-Anything issue #704：安装挂起 30 分钟静默）
- **建议**：对阿壹/阿贰及 codex200 调度链路中的关键工具调用做一次负路径自检：构造「工具必缺文件」「外部命令挂起」两类故障，断言 agent 能①识别失败而非被退出码 0 骗过，②超时后及时退出并上报，③释放执行槽位不让后续任务饿死。CLI-Anything 的 30 分钟静默挂起是现成的反例教材。
- **作用于**：work-profile #2（多机协同可靠性）、#3
- **预期收益**：无人值守 agent 体系最大的隐性风险不是做错，而是「卡住但不报错」；一次自检能暴露我们调度器（codex200-run.js --chain 依赖前步产物）的同类隐患。
- **成本**：低，约 1 人日，主要为构造故障场景与验证。
- **风险**：低；若发现真问题，修复范围可控（超时与重试参数）。
- **下一步**：采纳后司令列出工具链清单（每步的失败语义现状），用户圈定优先自检的 3-5 个环节。

- **建议**：盘点我们的离线负载（eval 跑批、报告生成、代码扫描批量任务），测算切换 batch 定价（5 折）的年化节省与延迟代价。**前置条件**：W47 ACT-1 的轨迹数据落地后才有真实调用量口径；在此之前只做测算不动配置。

## 四、思考

1. **本周验证层主线的关键词从「验证」变成了「失败语义」。** W47 我们说的是「验证层决定自改进上限」，那是价值判断；本周 OpenAI 演示、Claude Approvals、Text-to-SQL 评判模型给出的全是失败路径的工程定义：拒绝后不该发生什么、执行后指标不恢复算什么、评判器换业务库后保证还剩多少。这说明行业已经过了「要不要验证」的争论，进入「失败也写成可执行断言」的阶段。对我们的直接含义：W47 的 ACT-4（三态用例）如果只覆盖成功路径，等于只做了一半——所以本周 ACT-2 直接补上两条负路径，且与 ACT-4 合并落地最省成本。
2. **Sashiko 给我们的不是「AI 审查能行」的信心，而是「数据先行」的纪律。** codex 11-23 的校准很有说服力：同一个 Sashiko，司令头条里的三个数字（528 CVE、75.8%、返修率降 35%）统计对象各不相同，直接搬用会高估。真正可迁移的是它的对照实验方法：固定模型与推理档位、20+20 分组、同时报告命中/误报/成本。我们内部推 AI Review 的最大阻力一定来自误报，ACT-1 的对照集就是把这个问题前置量化。
3. **「策略托管审批」是效率解药也是新风险面。** Claude Approvals 这类「按仓库策略自动批」的方向和 ai-loop 11-26 洞察（HITL 从「人管每次」到「人管例外」）一致，也是我们多 agent 体系想要的终态；但 Reddit 那句「能写分支的 Agent 也会读到不可信的 PR 内容」点破了要害——策略本身可能被 prompt 注入操纵。落地顺序必须是：先有「策略会放行、人工最终拒绝」的统计（说明策略过松），再谈自动批准。我们不必抢这个功能，但统计口径现在就可以埋。
4. **大瓜的两条长期判断**：① OpenAI 成本控制模式若属实，叠加本周 batch 5 折与 flash 价格战，说明「推理成本通缩」是行业性而非单一厂商现象——对我们是利好（降本窗口），对供应商选型的含义是别签长周期高价合约；② Google MCP 官方化+能力阉割与 stitch-skills 的「标准宣讲 vs 工程质量」落差是同一件事的两面：**开放标准正在被巨头收编为生态锁定工具**。我们坚持 Agent Skills 开放标准（ACT 观察项）没错，但对「官方实现」要多一层核验，标准兼容不等于能力完整。
5. **对 codex 校准的吸收**（本周四篇：daily/trending/llm-rankings 11-23、11-25、11-27 + W48 周报）：Sashiko 统计口径拆解、Azure SRE Agent GA 时间更正、stitch-skills 检查器返回 0 的反例都直接修正了司令报告的结论强度。W48 周报对我 11-27 头条的偏航判定（从单一评测榜推及「编码能力整体领先」）成立，已在本报告修正为「BenchLeader 编码评测榜上 Claude 领先」这一受限表述。周报的核心增量是「验收要同时保留正例与反例」：TASK Memory 的近邻反例设计（39.2%→7.5%）给我们两个提醒——(a) ACT-1/ACT-2 的用例组同样要含「相似但不适用」的负例，不是只测会失败的任务；(b) 我们自己的 MEMORY.md / daily notes 记忆机制没有反例自检，记忆污染（过时事实、相邻条目误用）是下周 codex 记忆主题（25% 权重）值得观察的方向。trending「星数≠采用度」的纪律继续收紧：46.9 倍 vs 1.65 倍的案例说明组件级加速与端到端收益必须分开陈述，本报告引用数字时沿用此口径。
